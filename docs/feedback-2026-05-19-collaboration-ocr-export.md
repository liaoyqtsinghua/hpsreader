# 2026-05-19 使用反馈：协作、OCR 与导出

本文档记录本轮实际使用中需要进入后续开发排期的问题。优先级以“是否阻塞真实研读和产出”为主要判断标准。

## 1. 群组协作功能

- 类型：产品功能 / 多用户协作
- 优先级：高
- 状态：待设计

当前版本以本地单人研读为主，但实际使用场景中需要多人围绕同一文档、项目或翻译任务协作。

需要明确的能力：

- Project 可以邀请多个成员参与。
- 成员有不同权限：Owner、Editor、Reviewer、Reader。
- 批注、术语、翻译、笔记需要记录作者、时间和修改历史。
- 支持围绕段落、页码、术语或选中文本发起讨论。
- 支持任务分配，例如 OCR 校对、术语统一、译文审校、导出整理。
- 支持冲突处理，避免多人同时覆盖同一段译文或同一条术语。

初步技术方向：

- 先实现本地/单机的“协作数据模型”：`members[]`、`comments[].authorId`、`events[].actorId`、`tasks[]`、`revisions[]`。
- 再实现服务端同步能力：项目级协作 API、权限校验、变更日志。
- 短期可以先做“导入/导出协作包”和“按用户筛选批注/任务”，不立即实现实时协同编辑。
- 长期可考虑 WebSocket 或 CRDT，但不要在数据模型未稳定前直接引入复杂实时协作。

验收标准：

- 用户可以为项目添加成员，并给成员设置角色。
- 批注、术语修改、译文修改都有作者和时间记录。
- 可以筛选“我的任务”“某成员的批注”“待审校段落”。
- 多人编辑同一段时不会静默覆盖，需要显示冲突或版本差异。

## 2. OCR 识别准确性与特殊字符处理

- 类型：OCR / 文档摄取质量
- 优先级：高
- 状态：待技术评估

当前 OCR 准确性仍可能不足，尤其是扫描 PDF、复杂排版、脚注、古典语言、带重音拉丁字母、希腊字母、数学符号和特殊标点。需要评估是否替换或增加开源 OCR 接口，并建立特殊字符处理策略。

### 2.1 是否更换开源 OCR 接口

不建议简单“替换”现有 OCR。更合理的方案是保留现有 Tesseract.js 作为轻量 fallback，同时增加可选 OCR Provider。

候选方案：

- Tesseract CLI：比浏览器/JS 封装更成熟，适合本地部署和多语言包管理。
- PaddleOCR：对中英文、复杂版面和部分扫描件效果通常更好，适合引入为高级 OCR Provider。
- OCRmyPDF：适合把扫描 PDF 转为带文本层 PDF，可作为预处理管线。
- Kraken / Calamari：适合历史文本、古籍或特定字体训练，但部署和训练成本更高。

建议路线：

- 短期：新增 OCR Provider 抽象，支持 `tesseract-js`、`tesseract-cli`、`paddleocr` 三类配置。
- 中期：增加 OCR 质量评估指标，包括 confidence、乱码率、特殊字符保留率、行块顺序异常。
- 长期：支持按项目/语言/文档类型选择 OCR Provider，并允许用户对某页重新 OCR。

### 2.2 特殊字符处理策略

特殊字符不能简单删除或统一替换。学术文献中，重音、希腊字母、连字、上标下标、破折号、引号、数学符号都可能承载含义。

处理要求：

- 原始 OCR 文本必须保留为 raw text，不允许只保存清洗后的文本。
- 清洗文本应另存为 normalized text，并记录清洗规则。
- 对疑似特殊字符错误生成 warning，不自动静默替换。
- 支持字符级或片段级校勘记录，后续可回溯到原图。

建议增加的数据字段：

- `segment.rawSource`
- `segment.normalizedSource`
- `segment.ocrWarnings[]`
- `segment.ocrConfidence`
- `segment.charIssues[]`

特殊字符规则建议：

- Unicode normalization 默认使用 NFC，避免破坏组合重音。
- 不默认使用 NFKC，因为它可能把具有学术意义的字符折叠为普通字符。
- 常见连字可以提示但不强制替换，例如 `ﬁ -> fi`、`ﬂ -> fl`。
- 希腊字母、重音拉丁字母、上标下标、数学符号应保留。
- 无法识别或置信度低的字符用可见占位标记，并绑定原图位置。

验收标准：

- 用户可以看到当前文档使用的 OCR Provider、语言包和置信度。
- 用户可以对单页或单段重新 OCR。
- OCR 结果中出现特殊字符或疑似乱码时，系统能显示 warning。
- 导出时可以选择导出 raw OCR、normalized text 或校勘后文本。

## 3. 导出功能优化：必须支持 Word 格式

- 类型：产出能力 / 导出
- 优先级：高
- 状态：待实现

当前导出能力需要进一步面向真实写作和交付场景优化。Word 格式是硬需求，不能只提供 Markdown、TXT 或 JSON。

必须支持的导出格式：

- DOCX（Word）：最高优先级。
- Markdown：用于版本管理和轻量编辑。
- PDF：用于固定版式交付。
- CSV/TSV：用于术语、批注、任务和审校表格。
- JSON：用于项目备份和迁移。

DOCX 导出需要支持的方案：

- 仅译文。
- 原文 + 译文对照。
- 译文 + 批注。
- 原文 + 译文 + 批注。
- 术语表。
- 项目研读报告，包括文档信息、术语、批注、任务、Agent 认知足迹。

DOCX 样式要求：

- 标题、一级/二级标题、正文、引用、脚注式批注应使用 Word 样式，而不是纯文本拼接。
- 原文与译文对照可使用表格布局。
- 批注需要清楚标注来源：原文批注、译文批注、页码、段落号、作者、时间。
- 支持页码范围、当前文档、整个 Project 三类范围。
- 文件名需要包含项目名、文档名、导出类型和日期。

建议技术方案：

- Node 端优先评估 `docx` npm 包生成 DOCX。
- 如果后续需要复杂版式，可评估 Pandoc 作为可选本地依赖。
- 导出服务应抽象为 `exporters/docx.js`、`exporters/markdown.js`、`exporters/pdf.js`，避免所有格式堆在一个文件中。
- 导出请求需要记录到项目事件中，便于追踪产出历史。

验收标准：

- 用户可在导出弹窗中选择 DOCX。
- 用户可选择导出内容、范围和布局。
- DOCX 能被 Microsoft Word 正常打开。
- 原文、译文、批注、术语表在 DOCX 中结构清晰。
- 至少提供一个自动化测试，验证 DOCX 文件可生成且包含核心文本。

## 建议排期

1. 先做 DOCX 导出，因为这是明确产出阻塞。
2. 同步设计 OCR Provider 抽象和特殊字符数据结构，避免继续累积不可回溯的 OCR 文本。
3. 群组协作先做数据模型和任务/作者记录，再决定是否做实时协同。
